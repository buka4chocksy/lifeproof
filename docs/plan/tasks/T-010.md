# T-010 — Walking skeleton: workspace create/list API

- **Task:** T-010 — Walking skeleton: workspace create/list API
- **Owner:** backend
- **Depends on:** T-005 (schema/RLS), T-006 (API contract), T-014 (list policy), T-015 (NULLIF hardening)

## Objective

Implement the walking-skeleton API slice in the NestJS app: a dev-mode identity, tenant-scoped DB access
under RLS, and the three workspace endpoints (`POST /workspaces`, `GET /workspaces`, `GET /workspaces/{id}`)
that create a workspace, emit an append-only `workspace.created` audit event, and list/read it — proving
"create a workspace → see it → audit it" end-to-end at the API layer.

## Acceptance (testable)

1. **Identity (dev-mode only).** A guard resolves an `IdentityPrincipal { sub, user_id }` from a
   `X-Dev-User-Id: <uuid>` header, gated to `NODE_ENV ∈ {development, test}`. In production the guard
   returns `401 auth.invalid_credentials` (no Auth0 integration yet). The guard ensures a **synthetic**
   dev user exists in `users` (lazy upsert by id; synthetic `email_ciphertext`/`email_hash`, no real PII,
   no plaintext email). Controllers never bypass the guard.
2. **Tenant-scoped DB access.** A helper runs each workspace-scoped operation in a transaction that does
   `SET LOCAL ROLE app_user; SET LOCAL app.current_user_id = <uuid>;` and, when scoping to one workspace,
   `SET LOCAL app.workspace_id = <uuid>`. With T-015's NULLIF hardening, an unset/empty GUC fails closed
   (no cast error). Never rely on `RESET` to yield NULL (D-020).
3. **`POST /workspaces`.** Validate with `createWorkspaceSchema`; generate the workspace `id` up front;
   in one transaction insert `workspaces` (owner = principal), insert the owner's `workspace_members` row
   (`role = 'owner'`), and insert an `audit_events` row (`action = 'workspace.created'`,
   `subject_type = 'workspace'`, `subject_id = id`, `actor_id = owner`, `request_id = X-Request-Id`,
   `workspace_id = id`). Return `201` + `Workspace` (snake_case). Return `409 workspace.name_conflict`
   when the unique `(owner_id, name)` constraint fires (SQLSTATE `23505`), and `422`/`400` on invalid
   input via `ErrorEnvelope`.
4. **`GET /workspaces/{id}`.** Return the workspace if the caller is owner/member (RLS enforces it),
   else `404 workspace.not_found`. **`GET /workspaces`** returns the caller's workspaces, cursor-paginated
   (`cursor`/`limit`, 1–100, default 20) with `{ data, next_cursor, has_more }`.
5. **Errors.** `ErrorEnvelope` everywhere; codes: `workspace.not_found` (404), `workspace.name_conflict`
   (409), `auth.invalid_credentials` (401), `auth.forbidden` (403), `internal_error` (500). Return
   `X-Request-Id` on every response and echo it into the audit event. Accept `Idempotency-Key` on POST
   (echo it; full 24h storage is a follow-up — note it, don't block).
6. **Contract updates.** In `docs/api/openapi.yaml`: add `workspace.name_conflict` to the error-code list,
   add a `409` response to `POST /workspaces`, and add `422` to `GET /workspaces` (invalid pagination).
7. **Tests.** Vitest: (a) unit — `createWorkspaceSchema` validation and the name-conflict mapping; (b)
   integration against Postgres (`docker compose up -d`) — create returns `201` and the `audit_events` row
   + owner membership exist; duplicate name → `409`; get-one returns `404` for a non-member; list shows
   only the caller's workspaces (cross-tenant isolation). This also satisfies the D-017 §4 repeatable RLS
   verification.
