## Acceptance (testable)

1. **Walking-skeleton flow spec** in `DESIGN.md`, covering exactly:
   - **Create workspace** — fields `name`, `type` (personal/family), `region` (defaults to `GB`, no
     hardcoded brand string), submit, and a plain-language security note (no "zero-knowledge" claim).
   - **Workspace dashboard** — an empty-state category-dashboard scaffold (category cards with a single
     primary "add" action), so the skeleton has a visible home after creation.
   - **"Workspace created" confirmation** — success state that includes a non-alarming hint that the
     action is recorded in the audit log.
2. **Component specs** (token usage + anatomy + states) for the minimal set: text field, select,
   primary/secondary button, card, empty state, progress indicator.
3. **States** for every screen: loading, empty, error, success, disabled, and unauthorized (per
   `DESIGN.md` §6). No blank screens.
4. **Accessibility acceptance** for these screens — WCAG 2.2 AA: keyboard-only, visible focus, labels,
   360 px viewport, reduced motion, and contrast using the existing tokens. List the axe checks that
   must pass in CI.
5. **Brand externalization** — reference a `brand.name` token placeholder; no hardcoded "LifeProof" in
   any public-facing copy spec (D-P0-02).
6. **API data contract note** — name the data each screen needs from T-006 (create needs `name`,
   `type`, `region`; dashboard needs the workspace list/empty state) so T-011 can wire without inventing
   fields.

## Definition of done

- `docs/design/DESIGN.md` updated with the walking-skeleton flow spec, component specs, required

- Any token addition reflected in `packages/design-tokens/src/index.ts` and documented in `DESIGN.md`.
- No frontend implementation (that is T-011).
